# setup-test-case

给项目搭一套能长期用的测试用例骨架。核心是一条约束：

> **样本放库外，断言放库内。**

大样本（几十 MB 的文档、图片包、数据快照）不进 git；仓库里只留「怎么验」——用例清单、断言基线、运行器。换机器只要有样本库就能跑，没有就整体 SKIP，不会把 CI 弄红。

## 会生成什么

| 位置 | 内容 | 进 git |
| --- | --- | --- |
| `<项目>/test-case/` | `README.md`、`manifest.json`、`expected/`、`fixtures/`、`runners/`、`config.example.json`、`.gitignore` | 是 |
| `<项目>/test-case/config.local.json` | 本机样本根的绝对路径 | 否 |
| `<样本库>/<项目>/` | `README.md` + 后续的用例目录 | 否 |

两份 `README.md` 都要写清**框架逻辑**——分层、命名、新增用例的步骤、执行命令、基线刷新纪律。它们是这套骨架能被别人接手的前提，不能省略、不能糊弄。

## 开始前：必须先读本机配置

读**本 skill 目录**下的 `config.md`。它记录这台机器上所有项目共用的存放约定。

### 情况 A：`config.md` 不存在 —— 这是本机第一次运行

**不要**自己猜一个路径就开始建。必须明确告诉用户并征求确认，例如：

> 这台机器上还没有 test-case 配置，这是第一次运行。我需要先确认三件事，之后会记到 `config.md` 里，以后就不用再问：
> 1. 本机所有项目的测试用例统一放在哪个根目录？
> 2. 那是本地盘、同步盘还是网络盘？（同步盘意味着多台机器都能看到，网络盘需要在线）
> 3. 分层用 `<根>/<账号>/<项目>` 还是 `<根>/<项目>`？

拿到答案后，把 `config.example.md` 复制为 `config.md`，按答案填写「全局约定」一节，再继续。

### 情况 B：`config.md` 已存在

直接读，把「全局根目录」「存储方式」「分层模板」作为后面推荐位置的依据。若「已归档项目」里已经有当前项目，优先复用那一行记录的路径，并在最后告知用户"沿用已有登记"。

## 第 1 步：摸清项目

先看再问，别上来就让用户填表。

| 要判断的 | 怎么判断 | 影响什么 |
| --- | --- | --- |
| 项目根 | `git rev-parse --show-toplevel`，失败则用当前目录 | 骨架落点 |
| 项目名 / slug | 目录名；有 `package.json`、`pyproject.toml`、`Cargo.toml` 时取其 `name` | `manifest.json` 的 `project` 字段 |
| 是否已有 `test-case/` | 看目录是否存在、是否非空 | 是否需要 `--force`，以及要不要提示用户合并 |
| 现有测试框架 | 找 `pytest`、`vitest`、`jest`、`go test`、`cargo test` 的痕迹 | 回报时告诉用户"这套和现有单测是并行的两层" |
| 大样本在哪 | 找 `fixtures/`、`samples/`、`testdata/` 里 >5 MB 的文件 | 提示迁移，但**不要自动搬**，等用户确认 |
| 是否已有 `.gitignore` | 有则不要整文件覆盖 | 只新建 `test-case/.gitignore` |

探测结果用两三行汇报，不要罗列全部命令输出。

## 第 2 步：推荐样本库位置

按 `config.md` 的分层模板拼一个路径：

```
<全局根目录>/<owner>/<slug>      # 分层含 owner 时
<全局根目录>/<slug>              # 不含 owner 时
```

把**推荐值**和**理由**一起给用户，并说明可以改：

> 建议把样本库放在 `D:/sync/test-case-data/me/my-app`（沿用 config.md 里的分层模板和同步盘约定）。要换别的位置直接说。

用户给出新路径时，用新的；**不要**因为和 config.md 不一致就拒绝，但要在最后提醒：这属于例外，建议在 `config.md` 的「已归档项目」备注里写明原因。

## 第 3 步：确认（不可跳过）

动手写文件之前，必须把下面四项列出来让用户确认。用户已经在本轮说过"直接建/已确认"的，可以略过重复确认。

| 确认项 | 示例 |
| --- | --- |
| 项目根 | `D:/code/my-app` |
| 骨架目录 | `D:/code/my-app/test-case/`（已存在则说明会覆盖哪些文件） |
| 样本库路径 | `D:/sync/test-case-data/me/my-app/` |
| 将生成的文件 | README ×2、manifest、config.example、.gitignore、runners ×4、fixtures/README、expected/（空） |

同时说明两件不会做的事：**不搬动现有样本**、**不改项目根 `.gitignore`**（只新建 `test-case/.gitignore`）。

## 第 4 步：生成

```bash
python "<本 skill 目录>/scripts/scaffold.py" \
    --project "<项目根>" \
    --slug "<slug>" \
    --name "<项目显示名>" \
    --data-root "<样本库绝对路径>"
```

| 参数 | 说明 |
| --- | --- |
| `--project` | 项目根，必填 |
| `--slug` | 小写 kebab-case，必填 |
| `--name` | 显示名，缺省用 slug |
| `--data-root` | 本项目在样本库中的目录，必填 |
| `--dry-run` | 只打印将写哪些文件，用来给用户过目 |
| `--force` | 目标非空时覆盖 |
| `--allow-inside` | 允许样本库放在项目内（默认拒绝，因为这等于样本进 git） |

脚本会拒绝两件事：样本库路径落在项目目录内、目标目录非空且没加 `--force`。遇到拒绝就回去和用户确认，不要绕过。

## 第 5 步：自检

生成后跑一次校验器，确认骨架能用：

```bash
python "<项目根>/test-case/runners/run_cases.py"
```

预期输出是 `PASS 0 | FAIL 0 | SKIP 0`（`cases` 为空）。若报错，按提示修，不要把错误留给用户。

再确认三个文件真的在：两侧 `README.md`、`manifest.json`、`config.local.json`。

## 第 6 步：回报

回报必须包含：

1. **两个 README 的绝对路径**——这是用户以后查规则的地方；
2. **样本库路径**，以及"样本怎么放"的一句话（`<样本库>/<用例id>/`）；
3. **怎么跑**：`python test-case/runners/run_cases.py`，以及退出码含义（0 通过或跳过，1 失败）；
4. **下一步**：放样本 → 在 `manifest.json` 登记 → `make_assert.py` 生成基线 → `run_cases.py` 验证。

不要在这四条之外堆一堆文件清单。

## 之后：新增用例

不要把新增步骤复述给用户——两份 README 里已经写全了。用户问起时指向 `test-case/README.md` 的第 5 节。

## 维护 `config.md`

- 每次成功建完骨架，在「已归档项目」表里追加一行：项目名、slug、样本库路径、日期、备注；
- 全局根目录或存储方式变了，只改「全局约定」一处；
- 不要把某次任务的一次性信息（issue 链接、临时路径）写进这个文件；
- `config.md` 是本地文件，绝不能提交到 git；`config.example.md` 才是入仓的模板。

## 边界

- **不搬样本**：发现项目里已有大样本，只提示，等用户确认后再动；
- **不动项目根 `.gitignore`**：只写 `test-case/.gitignore`；
- **不覆盖已有内容**：目标非空要 `--force` 且必须经用户确认；
- **不在 skill 文件里写具体项目信息**：模板全部用占位符，本 skill 自身保持项目无关；
- **不替用户决定路径**：推荐是基于 `config.md` 的建议，最终以用户确认为准。
