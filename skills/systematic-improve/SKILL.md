# 系统性改进（Systematic Improve）

## 用途

在实施用户的改进需求之前，先通过结构化的确认流程与用户对齐目标和方案，再动手修改。核心思想是"先对齐、后实施"：杜绝凭猜测修改，确保每一处改动都服务于项目整体。

## 整体流程

```
步骤一：全局了解项目情况
        ↓
步骤二：确认用户目标（一次一问，逐步澄清）
        ↓
步骤三：确认实现路径（方案多轮确认，最后留空供提问/自定义）
        ↓
步骤四：确认整体思路（目标 + 思路 + 涉及修改的文档）
        ↓
步骤五：决定接下来的路径（三条实施路径，用户选择）
        ↓
 ┌─────────────────┬──────────────────────┬──────────────────┐
 │ 直接按思路修改    │ 输出实施计划并确认      │ 先出设计文档       │
 │ （步骤六）       │ （步骤七）             │ （步骤八）         │
 └─────────────────┴──────────────────────┴──────────────────┘
```

步骤流转规则：

- 步骤一至步骤四必须按顺序完成。
- 步骤四中，用户对目标有修改意见 → 退回步骤一重新执行；对思路或涉及文档有修改意见 → 退回步骤三重新执行。
- 步骤五确定的实施路径不可跳过：直接修改进入步骤六；输出实施计划进入步骤七；先出设计文档进入步骤八。
- 执行任何步骤时，必须同时遵守文末的"核心原则"。

## 步骤

### 步骤一：全局了解项目情况

在执行后续任何步骤之前，必须先了解项目现状：

- 查看当前项目状态：文件结构、相关文档、最近提交记录。
- 定位本次需求涉及的功能模块，理解其现有逻辑。

### 步骤二：确认用户目标

先与用户确认目标，逐条澄清：

- 一次只问一个问题，逐步细化想法；如一个主题需要深入探讨，将其拆分为多个问题。
- 尽量使用选择题，开放式问题亦可。
- 每条消息只包含一个问题。
- 提问聚焦三个维度：目的、约束、成功标准。

### 步骤三：确认实现路径

确认用户目标后，先自行完整梳理实现过程，再将需要用户决策的路径或方案选择逐个与用户确认：

明确提示用户“如果对方案有疑问，可在最后留空处提问”。

- 一次只确认一个决策点，逐步确认。
- 提出带有取舍权衡的方案，以对话形式呈现，并附上推荐方案及理由。
- 先给出推荐选项，再解释原因。
- 通过选项菜单让用户选择方案
- 在选项最后留一个空位，供用户提问或写下用户自己的方案。
- 用户对方案的疑问可能持续多轮：解释后再次呈现选项，直到用户明确选择。
- 当用户在最后留空处提交内容时，先判断其性质：
  - 属于对方案的疑问 → 解释清楚后，再次弹出选项菜单，让用户决定。
  - 属于自定义方案 → 按用户方案继续推进。

### 步骤四：确认整体思路

完成步骤一至步骤三后，将目标、思路和涉及修改的文档，以对话形式与用户确认：

- 用户对目标有修改意见 → 重复步骤一至步骤三。
- 用户对思路或修改文档有修改意见 → 重复步骤三。

### 步骤五：决定接下来的路径

确认整体思路后，先说明三条路径的优劣，再根据本次调整内容的情况给出推荐，最终由用户选择：

| 路径 | 特点 | 适用场景 |
|------|------|----------|
| 直接按思路进行修改（进入步骤六） | 简单快速 | 修改较少，且不影响既有功能或内容 |
| 输出实施计划，确认后再修改（进入步骤七） | 用户可在实施前审核 | 修改较少，但内容可能涉及既有功能或逻辑，如新增判断分支、修改表格逻辑等 |
| 先出设计文档，后续结合 writing-plans、subagent-driven-development 等技能落地实施（进入步骤八） | 分步实施，每步采用"测试驱动开发（TDD）"模式，保证项目健壮性 | 修改较多，需将确定的需求分多步实施 |

### 步骤六：直接实施

按照用户已确认的目标、思路和涉及修改的文档，直接进行修改。

### 步骤七：编写实施计划并执行

根据已确认的目标和思路执行：

1. 编写实施计划，保存到 `docs/plans/YYYY-MM-DD-<topic>-plan.md`。
   - 遵循 Test-Driven Development (TDD) 的原则
   - 每一步均以一个独立的子任务（issue）来实现，确保每一步都可独立验证。
   - 每一步开发、测试通过后，提交 commit 才进入下一步。
2. 请用户审阅确认，并提示用户：如有修改意见，可直接在文档上修改。
3. 用户确认后，检查文档是否被修改：
   - 有修改，但未背离步骤四确认的目标和思路 → 审阅修改后的文档是否存在前后矛盾；如有矛盾，尽量不修改用户改动过的位置，而是调整其他位置解决冲突，然后重复本步骤，直到用户不再修改文档。
   - 有修改，且背离了步骤四确认的目标和思路 → 基于修改后的文档重新理解用户意图，从步骤二重新执行。
   - 没有修改 → 直接基于文档执行本次修改。

### 步骤八：输出设计文档

确认整体思路后执行：

1. 将确认后的设计写入 `docs/plans/YYYY-MM-DD-<topic>-design.md`。
2. 请用户审阅确认，并提示用户：如有修改意见，可直接在文档上修改。
3. 将设计文档提交 git。
4. 如需继续落地实施：
   - 询问用户："是否开始准备实施？"
   - 使用 `superpowers:using-git-worktrees` 技能创建隔离工作区。
   - 使用 `superpowers:writing-plans` 技能编写详细实施计划。
   - 可结合 `superpowers:subagent-driven-development` 技能分步实施，每步均采用"测试驱动开发（TDD）"模式，以保证项目整体性。

## 核心原则

执行以上所有步骤时，必须遵循以下原则：

### 原则一：不要猜测用户的意图

在确认用户目标和具体实现方案时，不对用户的意图做任何猜测；有任何疑问，都与用户确认清楚后再继续。

### 原则二：保证项目的整体性

在决定实施路径、编写实施计划或设计文档时，必须顾及项目的整体性，禁止"缝缝补补"式的实现方式。

示例：

- 涉及文档步骤调整时，不要在"步骤1"前面插入"步骤0"，而应整体调整步骤顺序并重新编号。
- 涉及更新文档表格时，先理解现有表格的逻辑，将新需求融合后，按新的整体逻辑重新形成表格，而不是简单地添加一行。
