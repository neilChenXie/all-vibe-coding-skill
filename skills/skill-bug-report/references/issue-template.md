# Issue 正文模板

按这个结构组织 issue。字段按实际情况增减：没有的信息可以写"无"或省略，但**问题描述、期望输出、测试用例**三项必须出现——它们是让作者能复现和验证的最小集合。

```md
## 问题描述

（用一两句话说清楚：用这个 SKILL 做什么时、出现了什么不符合预期的结果。附上关键报错或错误输出片段。）

## 复现步骤

1. （准备什么输入）
2. （执行什么操作，例如"运行 scripts/foo.py --input case.pdf"）
3. （观察到什么现象）

## 测试用例

- [<测试用例文件名>](<https://github.com/user-attachments/files/...>)

（如果测试用例是文本内容，也可以直接贴代码块；多个文件用列表逐行列出。）

## 期望输出

（**这份文件经过该 SKILL 处理后应该输出什么**。写具体结果：目标格式、关键字段、样例片段。不要写"应该正常工作"这种没法验证的话。）

## 实际输出

（实际得到的输出，或"未生成预期文件"之类的现象。长内容用折叠块或摘录关键部分。）

## 建议的解决方案

（怎么改。可以是方向性建议，也可以是具体到文件/函数的改法。没有建议就写"暂无建议，需作者评估"。）

## 环境

- SKILL：`<skill-name>`（仓库：`<owner/repo>`）
- 测试用例：`<文件名>`（大小：xx KB）
- 报告时间：<YYYY-MM-DD>
- 备注：（如果是 AI 构造的测试用例，在这里注明）
```

## 标题格式

```
[<skill-name>] <一句话问题摘要>
```

示例：

- `[pdf-to-md] 转换带合并单元格的表格时表头错位`
- `[md-to-pdf] 中文字体在 Linux 下回退成默认字体`

## 写作要点

- **标题**：包含 skill 名 + 症状，作者扫一眼就能判断归属。
- **期望输出**：这是最容易敷衍的部分。用户说的"这份文件应该输出的测试结果建议"就是它——写清楚输入文件应该被处理成什么，最好附一个最小样例。
- **测试用例**：必须是真实文件或可复现的文本内容；AI 构造的要注明。
- **一个 issue 一个问题**：不要在一个 issue 里混多个不相关的缺陷。
